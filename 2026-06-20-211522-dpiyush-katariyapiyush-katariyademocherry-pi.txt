● Confirmed the architecture. Here's the precise answer.

  Different repos → No impact. They're isolated. ✅

  The design is stateless per repo, so multiple instances on different repos do
  not affect each other:

  - Each browser tab / window gets its own session. In bridge.js, session is
  created fresh per connection (createBridge runs once per WebSocket / per
  Electron window). There's no shared global session.
  - The repo path travels with every command (msg.repoPath). Nothing is
  remembered globally between connections.
  - Git runs scoped to each repo's folder — every git call uses cwd: repoPath
  (verified in git.js, which has zero module-level state, just stateless
  functions).
  - Logs are per-repo — written to <repoPath>\cherry-pick-logs\, so each repo
  keeps its own.

  So: open as many tabs as you want, point each at a different repo (Repo A,
  Repo B, Repo C) — they run completely independently. Even web + desktop at the
  same time is fine (separate processes entirely).

  The one case that WILL conflict ⚠️: same repo, twice, at once

  If two instances point at the same repository and run operations
  simultaneously, they will clash — not because of this app, but because git
  itself has only one working tree, one HEAD, and one .git\index.lock per repo.
  Two concurrent checkout/cherry-pick operations on the same folder will corrupt
  each other or fail with a lock error.

  Rule of thumb: one active run per repo at a time. Different repos in parallel
  = safe; same repo in parallel = don't.

  A note on how the launchers behave here

  run-all.bat / the web launcher deliberately start one server and reuse it.
  That single server already handles many tabs/repos at once (each tab = its own
  isolated session), so you don't need — and won't get — a second server from
  re-running the bat. That's the correct setup for your "multiple repos" use
  case: one server, many tabs, one repo each.

● Why it's slow

  The time goes almost entirely into alreadyApplied() (the "is this commit
  already on the branch?" check). Here's the current backend, and why it's
  expensive — every call spawns a separate git process, sequentially:

  ┌──────────────────────────┬──────────────────────────────────────────────┐
  │           Work           │          git processes (sequential)          │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ commitInfo() per commit  │ 3 each — git log, git cat-file -p (parents), │
  │                          │  git log (parent label)                      │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ alreadyApplied()         │ For the last 200 branch commits → git show + │
  │ patch-id scan            │  git patch-id = ~400 spawns                  │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ plus a patch-id per      │ 2 each                                       │
  │ input commit             │                                              │
  └──────────────────────────┴──────────────────────────────────────────────┘

  So for, say, 20 input commits you get roughly 20×3 + 400 + 20×2 ≈ 500
  sequential git process launches. On Windows each launch is ~20–50 ms, so
  that's easily 10–25 seconds. That patch-id scan is the killer (it was the
  CLI's old O(n×100) problem).

  Yes — it can be made much faster

  Three changes, no behavior change:
  1. Patch-ids in ONE pipeline — git log -p | git patch-id computes all 200
  branch patch-ids in one streamed pass instead of 400 spawns.
  2. commitInfo from 3 calls → 1 — get parents via %P in the same git log (drop
  cat-file), and only look up parent labels for actual merge commits.
  3. Parallelize the per-commit lookups (bounded to 8 at a time) instead of
  one-at-a-time.
