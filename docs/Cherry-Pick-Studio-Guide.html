What it is

Cherry-Pick Studio takes a list of commit IDs and applies them, in the correct chronological order, onto a client branch — then pushes. It replaces the fragile interactive Bash script with a real UI that handles merge commits, conflicts, push retries, dry-runs, reviews, and crash-resume.

Two ways to run it

🌐 Web — opens in your browser (Express + WebSocket server).

🖥️ Desktop — the same UI packaged as an Electron app.

Both share one git engine and one frontend — only the transport differs.

You only need one of them — each works completely on its own. See How to run.

Why a UI instead of the script

The CLI had a swallowed merge-commit menu, a review-mode conflict bug, a global set -e leak, and resume blind-spots. The UI designs these out — decisions happen in dialogs, not fragile terminal prompts.

Packaged app — no Node.js needed

For handing the tool to someone who has not set up a development environment. One zip, nothing installed, and both modes work without Node.js.

Why this works: Electron's main process is Node. So the packaged app can open the desktop window and start the same Express web server internally — one bundle, both modes, no system Node.js.

Desktop and browser are separate sessions

The desktop window and a browser tab each get their own engine — they are not two views of the same session. Use one at a time for a given repository, or you could run two cherry-picks against it at once. Choosing a mode at launch (rather than switching mid-flight) is why there are two .bat files.

How to run (from source)

You only need to run ONE of them. The web app and the desktop app are two complete, independent versions of the same tool — not a pair that must run together. Each has its own built-in backend and the same git engine inside it. Pick whichever you prefer:
  • Web only (run-cherry-pick-studio.bat) → works completely on its own. You do not need the desktop.
  • Desktop only (run-desktop.bat) → works completely on its own. You do not need the web.
  • Both (run-all.bat) → only if you specifically want both windows open at once. It is a convenience, not a requirement.
Web users: keep the server console window open while you use the browser UI — that window is the backend. Closing it stops the web app.

Everything is a double-click. Three Windows launchers live in the project root:

To run BOTH (what you asked for)

  1. Double-click run-all.bat. That's it — it launches the desktop app and the browser UI in one go.
  2. A console window appears, checks Node + dependencies, then: the Electron window opens, and your browser opens to http://localhost:<free-port>.
  3. The web server keeps running in its own console window — leave it open while you use the browser UI. Close that window to stop the web server.

The 3 launchers explained

The .bat files are thin wrappers; the real logic lives in studio.ps1 (one PowerShell engine) so quoting and port handling are reliable even with spaces in the path.

run-all.bat                  ──►  powershell ... studio.ps1 -Mode all
run-cherry-pick-studio.bat   ──►  powershell ... studio.ps1 -Mode web
run-desktop.bat              ──►  powershell ... studio.ps1 -Mode desktop

Each launcher does:

  1. Find Node.js (via PATH, then standard install folders). Errors with the download link if missing.
  2. Ensure dependencies — runs npm install automatically if node_modules is absent.
  3. Web: asks the OS for a free TCP port, starts the server with that port, waits ~2s, opens the browser. Desktop: launches the Electron binary with the app folder.
No fixed port. The web UI never hard-codes a port. It requests a free one from the OS each launch, so a port already used by another process can never block it. If a server is already running, the launcher detects its actual port and just re-opens the browser there.

Combined launcher logic (run-all.bat)

It checks the web and desktop independently and starts only what is missing. So if one was killed, re-running run-all.bat brings back just that one.

Web running?Desktop running?What run-all does
yesyesStarts nothing — re-opens the browser to the running server.
yeskilledStarts only the desktop.
killedyesStarts only the web (on a fresh free port).
killedkilledStarts both.

Detection: a web instance = a node.exe running ...cherry-pick-studio...server.js (its listening port is read back via Get-NetTCPConnection). A desktop instance = an electron.exe whose path is inside the project.

How a run flows

  1. Pre-flight — validate the repo path, detect pending merge/rebase/cherry-pick, report a dirty working tree (offer auto-stash).
  2. Branch — fetch, confirm the branch exists on origin, warn about unpushed local commits, optionally check out fresh from remote.
  3. Commits — validate format, drop duplicates, resolve each ID, flag not-found.
  4. Plan — sort commits oldest→newest by timestamp, detect already-applied ones (exact hash + bounded patch-id scan), let you reorder.
  5. Run — the session cherry-picks each commit, pausing to ask you about merge parents, conflicts, and push failures; streams progress + a live log; writes a resume file after every commit.

Using the UI — 5 steps

  1. Repository — type/paste the path, pick one from the saved list (click ▾), or Browse in desktop mode, then click Check. Abort any pending op or auto-stash uncommitted changes here.
  2. Client branch — enter the branch (e.g. client/acme-release-2026Q1), Check it against origin, optionally Check out fresh from remote.
  3. Commits — paste commit IDs (comma or space separated) and Validate. Bad/duplicate/missing IDs are flagged.
  4. Options — choose push strategy, run mode, and an optional custom log folder.
  5. Review & order — Analyze & build plan sorts commits and marks already-applied ones; reorder if needed, then ▶ Start cherry-pick.

The right column shows a live progress bar, a per-commit status list, a final summary, and the running log. Decisions (merge parent, conflict, push retry, review commit) appear as modal dialogs.

Saved repositories

You should never have to retype a repository path. Every repo that passes Check is remembered, along with the branch you last checked out for it.

Click ▾ in the Repository field to open the list. Choosing a row fills the path, runs Check for you, and pre-fills that repo's branch in Step 2 — you still press Step 2's own Check, nothing is validated on your behalf.

ControlWhat it does
📌Pins the repo to the top of the list. Pinned repos are never dropped.
✕Forgets that repo. Nothing is ever removed automatically.
(missing)The folder no longer exists. It is greyed out but kept, so you can see what happened rather than wondering where it went — remove it with ✕ when you're ready.

Unpinned entries are capped at the 15 most recently used. The path is never filled in for you on startup, so Check can never run against a repo you did not choose.

Stored as plain JSON in config/repos.json (see Logs & where they go) — editable by hand if you ever want to.

Resuming an interrupted run

If a run is aborted part-way, it leaves a .cherry-pick-progress file behind. The next time you Check that repository you are asked what to do:

ChoiceEffect
ResumeLoads that session's branch and its remaining commits into the wizard, ready for you to validate and start.
Start freshDiscards the saved progress file and begins a new run.

The prompt names the repository and when the session was saved, so you can tell which run it is talking about.

A run that finishes never asks to be resumed. The engine deletes its own progress file on a clean finish, and the prompt only appears for a session that (a) belongs to the repository you just checked and (b) still has commits left. Earlier versions asked to "continue" runs that had already completed.

Run modes & push strategies

Run modes

Normal — cherry-pick and commit each commit individually.

Dry run — simulate only; reports what would happen (incl. merge prompts), changes nothing, writes a dry-run log.

Review — apply all with --no-commit so everything stacks as staged changes; at the end you review the combined diff and commit it as one commit (or discard).

Already-applied scan depth (Step 4)

Controls how many of the target branch's recent commits are patch-id scanned to detect commits already applied under a different hash (e.g. a previous cherry-pick).

Blank = 200 (default). Higher = catches older duplicates but slower. 0 = exact-hash match only — fastest, skips the patch scan entirely.

Tip: on very deep branches, lowering this is the single biggest speed-up for the Analyze step.

Push strategies

Push after each (safer) — pulls (ff-only) and pushes after every commit; smallest blast radius on failure.

Batch at end (faster) — one push after all commits succeed.

On push rejection you get a dialog: retry, force-with-lease, skip, or abort.

Running multiple instances / repos

Different repos → fully isolated. Open as many browser tabs / windows as you like, each pointing at a different repository — they do not affect each other.

Why it's safe: each connection gets its own session (no shared global state), the repo path travels with every command, git runs scoped to each repo's own folder (cwd: repoPath), and logs are written per-repo. One web server happily serves many tabs at once — each tab is its own independent session.

Same repo, twice, at the same time → will conflict. Not because of this app — git itself has only one working tree, one HEAD, and one .git/index.lock per repo. Two concurrent cherry-pick/checkout runs on the same folder will clash.

Rule of thumb: different repos in parallel = safe; the same repo in parallel = run one at a time.

Logs & where they go

Every run is logged inside the tool's own folder — not in your target repository. The main folder is created automatically:

cherry-pick-studio/
└── logs/
    └── 19-06-2026_AM/                 # PARENT — one per date + half-day (DD-MM-YYYY_AM|PM)
        ├── 11-41-32_AM/             # SUBFOLDER — a fresh one for each run (hh-mm-ss_AM|PM)
        │   ├── cherry-pick-log.txt   # full run log (each line timestamped + repo path)
        │   └── .cherry-pick-progress # resume state, rewritten after every commit
        └── 11-41-35_AM/             # the next run that day → its own subfolder
            └── ...
ItemDetail
Main folder<cherry-pick-studio>/logs/ — created on first run.
Parent folderPer date + half-day: DD-MM-YYYY_AM / DD-MM-YYYY_PM (e.g. 19-06-2026_AM).
Run subfolderA new subfolder for every run, named by start time hh-mm-ss_AM|PM (e.g. 11-41-32_AM). Same-second runs get a _2, _3 suffix.
Log filecherry-pick-log.txt (or dry-run-log.txt in dry-run mode). Header records the repository path; each line carries the exact time.
Resume file.cherry-pick-progress — records the repo path + branch and lets an interrupted run be resumed.
Custom locationSet a path in Step 4 → Log folder to override the default base.
Audit & error logslogs/tranclogs/ records every command and its inputs; logs/errorlog/ records failures. Both in .jsonl (queryable) and .log (readable).
Saved repositoriesconfig/repos.json — the list behind the ▾ picker. Plain JSON, safe to edit.

Where this lands in the packaged app

A packaged app cannot write next to itself — the bundle is read-only — so it uses your user profile instead:

%APPDATA%\cherry-pick-studio\data\
├── logs\                        # same date/run structure as above
│   ├── tranclogs\
│   └── errorlog\
└── config\repos.json            # your saved repositories

Paste %APPDATA%\cherry-pick-studio\data into Explorer's address bar to open it.

PointDetail
Why the profile?It also means replacing the app folder with a newer build keeps your logs and saved repos.
Why the data subfolder?Electron already owns %APPDATA%\cherry-pick-studio for its own browser cache. Keeping our files in data\ means clearing that cache can't take your audit trail with it. Leave the sibling folders alone.
OverrideSet the CPS_DATA_DIR environment variable to put everything wherever you like — including next to the .exe.
Each run is isolated. Runs are grouped under the day's parent folder, and every run gets its own timestamped subfolder — so logs never mix. The log header also records which repository the run targeted.
Why the tool folder? Your repositories stay clean — no cherry-pick-logs directory is ever written into them. All logs from all repos collect in one predictable place.

Troubleshooting

"Git is not installed" fills the whole screen

The app could not run git. Install Git for Windows with the default options and restart. If you believe it is installed, open a new terminal and run git --version — if that fails too, the installer did not add git to your PATH.

This check runs at startup deliberately, so you find out before filling in the wizard rather than at the first git operation.

"Windows protected your PC" when starting the packaged app

SmartScreen warns about any unsigned program. Click More info → Run anyway. It appears once per machine. If the file disappears instead, corporate antivirus quarantined it — ask IT to allow the folder.

The .bat says it can't find "Cherry-Pick Studio.exe"

The launcher looks for the .exe in its own folder. Keep Run Desktop.bat and Run Web (browser).bat next to the .exe — if you want a shortcut elsewhere, make a Windows shortcut rather than moving the .bat.

Web mode: how do I stop the server?

Close the small status window, or click Stop server in it. That window exists precisely to give you an off switch.

It asked to resume a run that had already finished

Fixed. A completed run now deletes its own progress file, and the prompt only appears for a session belonging to the repository you just checked and still having commits left. If you are on an older build, the Start fresh option clears the stale file.

"Electron failed to install correctly"

Electron's binary download didn't finish. Re-install just Electron:

cd /d "D:\Piyush Katariya\Piyush Katariya\DEMO\cherry-pick-studio"
npm install electron --force

The binary must exist at node_modules\electron\dist\electron.exe.

Desktop error: "Unable to find Electron app at D:\Piyush"

Caused by spaces in the path not being quoted. This is already fixed in studio.ps1 — make sure you launch via the .bat files (not a hand-typed command that drops the quotes).

Browser didn't open / port question

The web UI picks a free port automatically, so "port in use" can't block it. The exact URL is printed in the server console window (e.g. http://localhost:59964). If a server is already running, run-all.bat re-opens the browser to it.

"running scripts is disabled on this system" (PowerShell)

The launchers already pass -ExecutionPolicy Bypass, so the .bat files work regardless of your global policy. Always start from the .bat, not by double-clicking the .ps1.

Node.js not found

Install it from nodejs.org and re-run. The launcher checks PATH and the standard C:\Program Files\nodejs location.

Or sidestep it entirely — the packaged app needs no Node.js at all.

Stop the app

Close the Electron window to quit the desktop app. Close the server console window (or press Ctrl+C in it) to stop the web server. In the packaged app's web mode, close the status window.
