  2. Bug audit of cherry-pick-tool.sh

  These are what I found on a full read. Ranked by severity:

  Critical
  - Merge-commit handling is completely broken (handle_merge_commit, lines
  766–815, called at 1051). The function is called via
  merge_choice=$(handle_merge_commit "$id") — command substitution captures
  stdout. But every prompt (print_warn, parent list, the menu) prints to stdout
  too, so the entire menu text gets swallowed into merge_choice instead of shown
  to the user. The user sees nothing, and merge_choice ends up as a giant text
  blob → git cherry-pick -m "<blob>" … fails. Fix: all prompts must go to stderr
  (>&2), only the choice to stdout.
  - set -e leaks globally (e.g. line 923 in push_commits). The script starts
  with set -uo pipefail (no -e). The set +e … set -e pairs turn errexit on and
  never restore it, so after the first push the whole script runs under errexit
  — a later harmless non-zero (grep -q, etc.) can abort it mid-run. Fix:
  save/restore with set +e only, or use a subshell.

  High
  - Review-mode conflict resolution commits (handle_conflict, line 879). It
  always runs git cherry-pick --continue, which creates a commit — defeating
  review mode's --no-commit "one combined commit" model.
  - Crash detection misses custom log paths (check_crashed_session, line 142).
  It only searches SCRIPT_DIR/cherry-pick-logs. If you used a custom log folder
  (Feature 28), your progress file is never found on resume.
  - Destructive branch reset with no warning (gather_branch, line 344). git 
  branch -D force-deletes the local client branch to re-checkout from remote —
  any unpushed local commits on it are silently lost.

  Medium
  - Summary math is inconsistent (check_already_applied 548 vs
  do_cherry_pick 994). Pre-skipped commits add to SKIPPED but TOTAL_COMMITS is
  later set to only the remaining count, so Succeeded + Skipped can exceed
  Total.
  - Resume indices are wrong (save_progress/resume_session). After resume,
  COMMIT_IDS is the trimmed remainder but last_completed_index and
  [current/TOTAL] are computed against it, so progress numbers reset/mislead.
  - already-applied patch-id scan is O(n×100) (lines 515–528) — recomputes
  patch-ids for up to 100 branch commits per input commit; slow on big batches.
  - Misleading claim: disable_input (line 58) comment says keystrokes are
  "physically blocked," but stty -echo only hides echo — input still buffers.

  I'll hold for your own list before finalizing fixes — but note the CLI bugs 
  above will be designed out of the new UIs anyway (a real frontend replaces the
  fragile stty/command-substitution prompting entirely).
